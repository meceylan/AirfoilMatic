- **Faster mesh building and tests; settings file.** The app's mesh merges the nodes of its six blocks with NumPy instead of a Python loop over every node (about half of the build time; the mesh and the .msh file are exactly the same, tested against the previous code). The inflation-mode sizes (TE element at least 0.003c and 1.5× the last layer, Defeature Size, Curvature Min Size, far-field size) moved from the page script to `mesh.py` with their tests. The three library-wide mesh checks that used the same settings share one sweep. A new sidebar section, "Save / load settings", writes the section, domain, flow, mesh and sweep inputs to a JSON file and reads them back (known inputs only, types checked; an uploaded airfoil file is not saved).
- **Section library: 300 sections (was 200).** Rebuilt from the current UIUC database (coord_seligFmt.zip, February 2026; the coordinates of the sections already in the library are unchanged) with the same quality rules, the family quotas scaled by 1.5. Every section of the old 200 is kept. The undashed 6-series files are no longer skipped, so the real symmetric 64-012 and 64-015 are in the library (searching "64012" finds them). `tools/build_airfoil_library.py` takes `--target N` for another size; with 500 the small families run out and the same section enters twice under two file names, so 300 was chosen.
- **Pressure far field at low Mach.** A series of Fluent 2024 R2 runs (NACA 0012, 15c C-grid, mesh B, Transition SST, ideal gas + energy) found why the pressure-far-field setup did not converge: at M 0.15 and a non-zero angle the straight outer edge where the flow leaves at a shallow angle, and its rear corner, go unstable (the disturbance moves to the other edge when the angle changes sign), while the same case with a velocity inlet converges. Free-stream turbulence, ideal gas, energy and the mesh were ruled out one at a time. With the whole outer boundary as pressure far field and Time Scale Factor 0.2 it converged cleanly at M 0.3 (Cl 0.446, Prandtl–Glauert +0.9 %) and M 0.5 (Cl 0.496). Mach mode now says below M 0.3 to use velocity-inlet + pressure-outlet, the far-field note says to make the outlet far field too and what was tried, and the Named Selection help mentions it. At M 0.3 the default Time Scale Factor 1 gave the same Cl but the residuals stalled near 0.04 and the Convergence Conditions were never met, so 0.2 is recommended; Operating Pressure 0 with gauge 101325 (the way Mach mode gives the values) gave exactly the same result as Operating Pressure 101325 with gauge 0 (double precision).
- **Automation tab.** A third tab collects everything for running many angles: the angle-of-attack sweep table (moved from the Fluent helper on the Mesh / y⁺ tab, which keeps the single-angle helper and the turbulence decay), the Fluent journal and the new polar.
- **Mesh independence: grid family and GCI.** Next to the Fluent mesh file, a tick box makes three meshes from the same inputs, coarse / medium / fine, with the cell sizes changed by √2 (about 2x the cells per step; the medium mesh is the one shown; every size including the first cell changes with the family), downloaded as one ZIP with their cell counts and quality. The Automation tab starts with a one-line workflow and ends with a GCI section: enter the cell counts and Cl, Cd of the three meshes and it gives the order of convergence, the extrapolated value and the GCI of the fine mesh by the procedure of Celik et al. (2008, J. Fluids Eng. 130, 078001), and flags oscillatory convergence (checked against the worked example of the paper: p 1.53, extrapolated 6.1685, GCI 2.2 %). Tried in Fluent 2024 R2 (NACA 4412, 4°, SST k-ω, Re 2 × 10⁶, 42 944 / 84 870 / 169 824 cells, the three .msh swapped into one case with `/mesh/replace`): Cl 0.83552 / 0.83591 / 0.83529, Cd 0.012580 / 0.012567 / 0.012573. The three differ by less than 0.1 %, in an oscillating order, so the GCI section marks the convergence as oscillatory; the default (medium) mesh is mesh independent for this flow. Instead of typing the values, the three report files (.out) can be dropped on the GCI section: Cl and Cd are the mean of the last N iterations of each angle (as in the polar), a GCI row is given for every angle found in all three files, and an angle where a mesh's value has not settled is named. When the file names say coarse / medium / fine (or kaba / orta / ince), e.g. `naca4412_coarse.out`, the cell counts come from the mesh family of the current Mesh / y⁺ inputs (Mapped, C-grid) and stay editable; otherwise three files are matched to the cell counts typed in. Checked with the report files of the run above (the app's family gives the same 42 944 / 84 870 / 169 824 cells as Fluent).
- **Suggestions while typing in the section search.** The search is one box now: typing lists every library section (and common NACA codes) whose label contains the text, e.g. "64" → the 64-series sections, and a suggestion is picked with a click. A NACA code that is not listed, or another search, is typed and taken with Enter, as before. The second list ("sections found") only appears when such a search has more than one match. Before, the text box searched only after Enter, and a number with no section left both boxes empty. The dice and the ← → history fill the same box.
- **Fluent mesh file for the rectangular domain.** The app's .msh (and the coarse / medium / fine family) is now also made for the rectangle. The six blocks and the Edge Sizing plan are those of the C-grid; the side of each front block opposite the airfoil front is the chain the Ansys note describes: half of the inlet edge and the front segment of the top / bottom boundary, meeting at the inlet corner (the "Side" vertex), uniform with the table's divisions. Boundaries as in the Named Selection note: left edge, top and bottom are `inlet` (velocity-inlet), the right edge `outlet`. Quality, NACA 4412 at Re 2 × 10⁶: 84 870 cells as planned, max skewness 0.51, minimum orthogonal quality 0.67 (both at the inlet corners, where 90° is split into two cells; the C-grid has 0.30 / 0.895); every library section above 0.15 (tested). Tried in Fluent 2024 R2 (NACA 4412, the C-grid set-up case with `/mesh/replace` — the zone names are the same —, −4, 0, 4, 8°, SST k-ω, Re 2 × 10⁶, the app's journal): Mesh Check without error, minimum orthogonal quality 0.667662 in the same cell as the app computes; Cl −0.01082 / 0.41810 / 0.83723 / 1.22537, within 0.2 % of the C-grid; Cd 0.010343 / 0.010464 / 0.012418 / 0.016473, lower by up to 1.6 % at 8°, most likely from the domain shape (the whole top and bottom are velocity inlet, the corners are farther), not tested further.
- **Front axis along the wall normal (app's .msh, review group 3).** The block edge from the leading edge to the inlet was a straight horizontal line, tilted from the wall normal by the camber-line slope (NACA 4412: about 11°). Near it the grid lines turned into the axis direction, so the first-cell height measured normal to the wall changed from column to column; on cells 10⁴ times longer than high this alone dropped the orthogonal quality at high Reynolds numbers (NACA 4412 at Re 3 × 10⁷: 0.24, at 10⁸: 0.08; E63 0.004 at 3 × 10⁷, below Fluent's 0.01). The front axis now leaves the leading edge along the wall normal (bisector of the upper and lower normals) and bends to horizontal within one chord, and the first-cell heights near the wall come from the planned distribution of the side edges instead of each interpolated line's own length (which varies by about 0.7 % between columns). NACA 4412: Re 3 × 10⁷ 0.24 → 0.59, 10⁸ 0.08 → 0.24, default Re 2 × 10⁶ skewness 0.37 → 0.30 and orthogonal quality 0.845 → 0.895. Whole library (coarse family mesh): lowest orthogonal quality at Re 2 × 10⁶ 0.051 → 0.15, at 3 × 10⁷ 0.004 → 0.013, no turned-over cell (tested). Thin leading edges stay the weakest at very high Re: the corner between the upper and lower surface cannot be normal to both. The exported DesignModeler / SpaceClaim geometry keeps the straight axis. Nodes in front of the leading edge move by up to 0.066c. Tried in Fluent 2024 R2 (NACA 4412, the set-up case with `/mesh/replace`, −4, 0, 4, 8°, SST k-ω, Re 2 × 10⁶, the app's journal): Mesh Check without error, minimum orthogonal quality 0.894628 in the same cell as the app computes; Cl −0.01082 / 0.41741 / 0.83585 / 1.22288 against −0.01079 / 0.41741 / 0.83588 / 1.22287 on the earlier mesh, Cd within 0.05 %.
- **Usability fixes from the code review (2026-11-27).**
  - An uploaded airfoil file is kept when the source is switched to the search and back (Streamlit empties a hidden file uploader); the sidebar says which earlier file is used.
  - The "no section matches the filters" warning goes away once another section is chosen.
  - Mach mode below M 0.3 shows a one-line warning; the Fluent run behind it is under "Why?".
  - In the use-as-drawn mode the split-line boxes are disabled (they had no effect there).
  - GCI: a ± column gives the uncertainty in the value's own units (the % means little near Cl = 0), a refinement ratio below 1.3 (Celik et al. 2008) is warned about, and the section names the report-file columns it read. The column guess no longer takes a force report such as `cl-alpha-report` for the angle, nor `cdconv` for Cd.
  - Report files: rows with `nan` are skipped (an angle's mean became nan and was still marked steady); separate files of separate report definitions (one column each) are joined on the iteration.
  - The even-step sweep is limited to ±180°, as the own-angle list already was; own angles are rounded to the 4 decimals the journal writes.
  - A 5-digit NACA code with design-lift digit 0 (e.g. 01012) is refused, as the 4-digit reader refuses 0312.
  - The .msh file and the family ZIP are written only when their download button is clicked, the download no longer reruns the page, and a spinner shows while a mesh is built (with the family ticked every change took about 3.7 s without feedback).
  - The speed in the Fluent helper shows significant digits (it read 0.000 for very slow flows).
  - The automatic tests also run on Python 3.14, the version Streamlit Cloud uses.
- **Fixes from an independent code review (2026-11-27).**
  - The app's .msh put the chordwise spacing on the wrong ends when the leading- or trailing-edge element was larger than the one at the split line (e.g. ds_le 0.02, ds_split 0.005 gave 0.005 at the leading edge and a 4× jump at the split line). The Edge Sizing table was right; only the mesh file was affected.
  - The mesh file is limited to 1 000 000 cells (about 90 MB of text; with the family ticked the fine mesh counts). Smaller element sizes, a target y⁺ of 0.05 and a growth ratio of 1.01 could ask for 0.9–2.6 million cells, built at every change, on a hosted app that has 1 GB for all users. Above the limit the app says so instead of building the mesh.
  - GCI: the order of convergence is now bracketed and bisected on 0.0001–20 instead of the fixed-point iteration, which overflowed, divided by zero or stopped on a wrong p when the two refinement ratios differ (typed-in cell counts, Ansys meshes; the app's own √2 family was mostly safe and its NACA 4412 result is unchanged). With two solutions the smaller p is taken (larger, safer uncertainty); with none the app says so. A mesh series whose difference grows as the mesh is refined (monotonic divergence, Stern et al. 2001) is shown as diverging, without p or GCI.
  - Polar: in a sweep continued from a saved case, every row of the abandoned run from the first iteration of the continued run on is dropped. Before, rows beyond the end of the continued run survived, so an angle that diverged for 2000 iterations and then converged in 300 kept its bad block.
  - Uploads up to 50 MB (was 2 MB; an 11-angle report file is already 0.93 MB).
  - The journal inputs (iterations, expression, save interval, folder), the family tick box and the polar / GCI settings keep their values while they are hidden (e.g. while the own-angle list is empty).
  - Orthogonal quality: the cell centroid is computed relative to the cell's first node; with absolute coordinates the result changed when the mesh was moved (very thin cells at high Re).
- **Vertical columns above and below the rear of the airfoil (app's .msh).** The far top and bottom edges of the two rear blocks (split line → trailing-edge line, at ±15c) now take the x positions of the airfoil's surface nodes instead of the table's fractions. On a strongly cambered section the surface falls steeply towards the trailing edge, so its cells were shorter in x than those of the far edge and the cells in between slightly trapezoidal; at the far boundary they are 0.0009c wide and 1.36c high, and that taper alone moved the cell centroid enough for orthogonal quality (Fluent's definition) to read 0.06 on NACA 9940, 0.08 on S9104, 0.12 on FX 73-CL2-152 and 0.20 on S1223 (15 library sections were affected). With vertical columns their lowest orthogonal quality is 0.27 / 0.41 / 0.61 / 0.62, now at the trailing edge, and every library section has at least 0.3 in the far field (tested). Cell count, block edges and the Edge Sizing table (Ansys path) are unchanged; on thin sections the far edge spacing is almost the table's. If the surface x does not increase towards the trailing edge (a hooked edge) the table's fractions are kept. NACA 4412 moves by at most 0.0034c (1e-5c near the airfoil). Tried in Fluent 2024 R2 as part of the bent-axis NACA 4412 mesh (same Cl / Cd as before).
- **Grid lines leave the wall at right angles (app's .msh).** On the two front blocks (leading edge → split line) the grid lines now start along the wall normal and join the interpolated lines within about half a chord; the block edges, the cell count and the Edge Sizing table are unchanged, and so are the DesignModeler / SpaceClaim outputs. Plain transfinite interpolation let the lines leave the wall almost along it behind the nose of strongly cambered sections (S9104, 14 % camber, concave lower surface near the leading edge): skewness 0.90 and orthogonal quality 0.05 in the first cells. Now S9104 has 0.64 / 0.54 at the nose, E377 0.97 → 0.76, NACA 4412 0.52 → 0.37 (minimum orthogonal quality 0.49 → 0.84), NACA 0012 0.40 → 0.28. Every section of the library meshes without a turned-over cell (tested). Two sections stay weak at the leading edge (E63 orthogonal quality 0.08, was 0.05; S6063 0.20, was 0.31). The very steep trailing edge of extreme sections (NACA 9940, S9104) still has distorted cells; that is a separate step. Tried in Fluent 2024 R2 (NACA 4412, the set-up case with `/mesh/replace`, −4, 0, 4, 8°, SST k-ω, Re 2 × 10⁶, the app's journal): Mesh Check without error, minimum orthogonal quality 0.844962 in the same cell as the app computes; Cl −0.01079 / 0.41741 / 0.83588 / 1.22287 against −0.01088 / 0.41739 / 0.83590 / 1.22338 on the earlier mesh, Cd within 0.2 %, every angle stopped by its convergence condition. The Fluent runs listed under the .msh entry were on the earlier mesh.
- **Fluent mesh file (.msh) from the app.** With Mapped selected (C-grid), the Mesh / y⁺ tab offers a Fluent mesh file the app builds itself: the six blocks with the divisions and bias factors of the Edge Sizing table, the inside filled by transfinite interpolation that follows the edge spacing, boundaries named `inlet` (velocity-inlet), `outlet` (pressure-outlet) and `wall`. Read it in Fluent with File → Read → Mesh or swap it into a set-up case with `/mesh/replace`; DesignModeler and Meshing are not needed. The app shows the cell count (equal to the planned count) and the worst skewness and orthogonal quality, computed with Fluent's definitions. Face orientation follows Fluent's rule (c0 left of n0 → n1, c1 = 0 on a boundary), checked against a .msh file written by Ansys Meshing 2024 R2. For NACA 4412 at Re 2 × 10⁶: 84 870 cells, max skewness 0.52 (Ansys from the same table: 84 501 cells, 0.45). Fluent 2024 R2 read the file (also into a set-up case with `/mesh/replace`, boundary conditions kept) and Mesh Check found no error; its minimum orthogonal quality, 0.493 near the leading edge, is what the app shows (the app uses the area centroid of each cell, as Fluent does). Solved in Fluent 2024 R2 (NACA 4412, −4, 0, 4, 8°, SST k-ω, Re 2 × 10⁶, the app's journal): Cl and Cd equal those on the Ansys mesh within 0.01 % and 0.05 % (Cl −0.01088 / 0.41739 / 0.83590 / 1.22338 against −0.01086 / 0.41739 / 0.83596 / 1.22337). The rectangular domain was added later the same day (see below). With a blunt trailing edge the outlet edge copies the spacing at the trailing edge (the rows behind the base and the shear layer from the corner run straight to the outlet); the single bias of the table's outlet row made the rows cross the wake there and the cells at the outlet badly distorted. The blunt trailing-edge closure (also its row in the Edge Sizing table) now starts with the first-cell height at both corners and grows at the wall-normal ratio towards the wake axis (two-way bias, largest in the middle): with equal cells, 0.9 mm next to the 0.012 mm first cell of the trailing-edge line, the size jumped 72-fold along the whole wake from the corner and Fluent 2024 R2 diverged at once on the GA(W)-1 (LS(1)-0417) mesh. With the new closure the same case converged at −4, 0, 4, 8° (91 122 cells; Cl −0.0152 / 0.4453 / 0.8801 / 1.2501, Cd 0.0118 / 0.0121 / 0.0147 / 0.0201; zero-lift angle −3.87°, thin-airfoil theory −4.27°).
- **NACA 4412 runs: mapped mesh and the use-as-drawn mode tried (Fluent 2024 R2).** A 6-block mapped mesh from the section search (84 501 quads, the app estimated 84 870) and the use-as-drawn mode from a Selig file with inflation (47 674 elements) gave the same result within 1.5 % in Cl and 2 % in Cd at −4…8° (SST k-ω, Re 2 × 10⁶); zero-lift angle −3.90° / −3.98°. The use-as-drawn note on the airfoil edge sizing now gives the tried example (upper 266 / lower 258 divisions, bias 10, small end at the leading edge). README: the comparison, a tip for `/mesh/replace` (move a set-up case to a new mesh), one bias for the wall-normal edges, and the SpaceClaim / SolidWorks outputs marked as tried by users.
- **Stall notes in the polar.** A steady solution that oscillates is not always stall: in Fluent 2024 R2 (NACA 0012, SST k-ω, Re 2 × 10⁶) the steady Cl at 16.99° swung between 0.30 and 1.35, and URANS (Δt = 0.01 c/U, 3000 steps) settled to attached flow (Cl 1.46, Cd 0.045; Ladson's experiment has stalled: 1.09 / 0.249). The warning for oscillating angles now says this and points to URANS. A model note under the polar: fully turbulent SST k-ω matched Ladson's Table IX up to 15° with Cl 2.5–3.5 % high and gave stall late. A transient report file (first column Time Step) is read too; the table then counts time steps, with a note to average over whole periods. README: the angle sweep and stall comparison.
- **Your own angles.** The sweep takes either even steps (first angle, last angle, step) or your own list of angles, e.g. `1.3, 2.8, 6.8` to match the angles of an experiment. The table and the journal use the list; angles are sorted and repeats are taken once. The decimal mark is a dot; a comma between two digits (`1,3`) is refused because it could be a decimal comma or two angles. Angles must be at least 0.01° apart, because file names hold the angle to 2 decimals. Tried in Fluent 2024 R2 with Ladson's test angles (1.99, 4.01, 6.11, 8.08; SST k-ω, velocity-inlet case): the journal ran without a question and every angle stopped by Convergence Conditions. The velocity-inlet lines were copied from the app in the same run (`51.04 [m s^-1]*cos(aoa)`; Fluent accepted the unit and the result matched the hand-written `[m/s]`).
- **Polar from the report file.** Upload the report file (.out) Fluent wrote during the sweep. The columns are found by name (Fluent writes them in alphabetical order; angle, Cl and Cd can also be picked by hand), the angle column is read in radians by default (an expression report of a [deg] expression is written in radians) or in degrees. Each angle is the block of iterations in which it stays the same; the table gives the mean of the last N iterations (default 50), the max – min range of Cl and Cd over them, Cl/Cd, the iteration range and a status: steady, oscillating (Cl moves more than 1e-3 or Cd more than 1 % over the last N iterations; both limits adjustable) or few iterations. If an angle was run again later the latest block is used, and iterations written twice by a sweep continued from a saved case use the later lines. Cl–α, Cd–α and Cl–Cd charts with the range as error bars, and a CSV. Tried with the report file of the 11-angle NACA 0012 sweep (Fluent 2024 R2): −4…6° steady, 8–16° oscillating, as in the table worked out by hand; at 10° the mean of the last 50 iterations gives Cl 1.043, Cd 0.0131 (Ladson 10.15°: 1.045, 0.0135) where the last value was 1.056.

- **Fluent journal.** On the Automation tab, under the angle sweep table (angles always run from the smallest to the largest), there is a download of a Fluent TUI journal (`.jou`) and a list of what the case needs. You set up the case in Fluent yourself: a named expression `aoa` (the angle), the pressure-far-field flow direction X = `cos(aoa)`, Y = `sin(aoa)` or the velocity-inlet components `U [m s^-1]*cos(aoa)`, `U [m s^-1]*sin(aoa)`, and Cl and Cd as expression report definitions that use `aoa` (the app prints the exact expressions with your density, speed and chord; report files should hold only expression reports and the moment, because a changed force-vector lift/drag report makes Fluent ask a question about its file, and inside a journal the next line becomes the answer). Residual convergence checks off; set `aoa` to the first angle, initialise and run at least one iteration yourself. At each angle the journal only changes the expression (`/define/named-expressions/edit aoa definition "6 [deg]" q`), runs the chosen number of iterations (default 1000) and continues from the previous solution. Inputs: iterations per angle (an upper limit: with Convergence Conditions in the case, Fluent ends an angle early and the journal goes on to the next one), expression name, how often case and data are saved (every k angles, the last angle always; 0 = only the last angle) and the save folder. The setup list also gives `clconv` = Cl + 1, an expression report to use instead of Cl in Convergence Conditions: Fluent's criterion is a relative change, so at an angle where Cl ≈ 0 (a symmetric profile at 0°) it is never met and the angle runs to the iteration limit (seen in the 11-angle sweep); Cl + 1 stays near 1, so its relative change is the absolute change of Cl. Tried in Fluent 2024 R2: at 0° the angle stopped by itself after 366 iterations with the same Cl and Cd as the 2000-iteration run. To continue a stopped sweep: read the last saved case and data and run one iteration by hand; Fluent asks "Do you want to create new file?" for every report file (the file already holds later iterations), answer Yes and the rest goes to `<name>_<iteration>.out`; then set the first angle to the next angle and download a new journal. Tried in Fluent 2024 R2 (−4…4°, Fluent closed while 2° was running, continued from the 0° save): the result matched the uninterrupted sweep. The polar tool takes the old and the new report file together; where both hold the same iteration, the file that starts later wins, so the iterations of the cut-off angle are dropped. Cl and Cd come from the report files, one block of iterations per angle. Tried in Ansys Fluent 2024 R2 (standalone, 2D): the edit command, the Cl/Cd expressions (same values as Fluent's force reports to about 1e-6) and the report files (no question asked after changing the expression). A 3-angle sweep (−2°, 0°, 2°, 50 iterations each) ran to the end without a question, and so did an 11-angle sweep (−4° … 16°, up to 2000 iterations each, Convergence Conditions, velocity-inlet case). So did a sweep with a pressure-far-field case (M 0.3, 2…8°, the whole outer boundary far-field, Time Scale Factor 0.2): 2° and 4° stopped by Convergence Conditions, 6° and 8° reached the 1000-iteration limit with steady values. Fluent inside Workbench was tried and does not work: it asks "Settings have changed in Fluent" at every angle change, again even after "current and future calculations" was chosen; the journal is for standalone Fluent. Not tried yet: overwriting a case file with `/file/confirm-overwrite? no`. Read it with File > Read > Journal.
